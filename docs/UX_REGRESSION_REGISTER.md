# ElliePdf UX regression register

Status: R0 source audit / proposal. This register is evidence from source inspection only; it contains no screenshot or desktop-test claims and does not infer user approval. Comparison points are candidate baseline `363243e`, current `HEAD 4184526`, and the working tree as inspected on 2026-09-07. The recovery plan is the governing scope: [UX_DESIGN_RECOVERY_PLAN.md](UX_DESIGN_RECOVERY_PLAN.md), especially R0, R2, the journey matrix, and the requirement to classify uncommitted work as retain/rework/unverified.

## Reading the dispositions

`Retain` means the source presents a credible capability or safety improvement worth preserving while the shell is repaired; it is not a pass. `Repair` means the current affordance is hidden, narrowed, or structurally risky and needs an owned UX/interaction decision. `Defer` means a feature may remain outside the exemplary reading slice until the user explicitly chooses its priority. `Unverified` means source presence is not evidence that the real journey works. “Owner” is a proposed role, not an assigned person.

## Known smoke failures and limits from the recovery plan

These are reported by the plan, not newly reproduced in this audit:

- Direct user acceptance failed: the result looked worse and functions were hard to find.
- Commands lacked visible labels; `DefaultLabelPosition=Collapsed` and overflow hid important actions.
- Single-document identity was weak because the tab strip appeared only when `TabCount > 1`.
- A pane-close hit target could close the application; the 50-pixel margin was recorded as a stopgap, not a fix. Current source still has explicit shell offsets (`MainPage.xaml:14`, `Pages/ReaderPage.xaml:345-358`) requiring coordinated title-bar review.
- Text drag/double-click/copy failed on a vector fixture; root cause was not established.
- Encrypted open silently retained the prior document without a password prompt; the plan notes a possible UI-thread-affinity hazard, not a proven precise runtime path. Current prompt dispatch is in `Dialogs/WinUiPdfPasswordPrompt.cs:16-52` through `UiHostContext`.
- Initial F5 launch crashed during XAML initialization; title initialization subsequently allowed launch. This is a fresh-install/F5 regression check, not product readiness.
- Rendering, page navigation, zoom and one search worked only on limited vector-fixture smoke evidence.
- Forms/save-copy, corrupt files, multi-tab workflows and long-document interaction remain unverified.

## Action priorities and ownership

1. **P0 — Shell and input integration (shell/interaction lead):** resolve title-bar/caption/pane hit testing; make document identity and primary commands visible; reproduce selection/copy and password/open state transitions in a real window.
2. **P1 — Parity decision (product/design + edit owner):** side-by-side source inventory for shape tools, redo, rich signatures and organizer entry; mark each retain/repair/defer with explicit user decision. Do not hide a missing feature behind Labs and call it complete.
3. **P1 — Exemplary reading slice (reader owner):** prove launch → open → identify → read → select/copy → Find → page → zoom/fit → close, including empty/loading/error and keyboard paths.
4. **P2 — Journey completion (forms/organizer/print owners):** run the plan's full matrix for forms/save/reopen, organizer, print, links, permissions, recovery and long documents after the shell contract is stable.

## Acceptance record format

Every row that moves out of `Unverified` should link to a reproducible record containing: fixture and privacy status, source commit/package/configuration, hardware/window/theme/scale, exact steps, expected and actual outcome, owner, severity, and evidence (screenshots/recording/logs where available). A source reference in this register is an audit trail, not evidence that the behavior passed. No row is “approved” until the user accepts the actual application as required by R1/R5.
